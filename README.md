# Nucleus

Core shared library for Nuclear Nightmare mods: a C++ DLL (weak object handles, a monotonic clock), a LogicMods Blueprint pak (the `Nucleus_Call` channel and the widgets `WBP_NucleusText`, `WBP_NucleusPanel`, `WBP_NucleusButton`, `WBP_NucleusList`, `WBP_NucleusRow`, `WBP_NucleusScreen` and `WBP_NucleusImage`, and core's icons `Icons/T_*`, and the replicated `NucleusNet`) and Lua (bootstrap, `connect`, logging, the HUD UI helpers `core.ui`, the settings service `core.settings` and the host's replicated values `core.net`).

Spec, API contract and stories: `_bmad-output/specs/spec-core-v0/` in the workspace repo (they still say `NNCore`, the old working name).

```powershell
$inst = 'C:\...\nuclear-nightmare\game-instances\v8.1.2-build26193463'   # absolute, also from a worktree
./build.ps1                                   # native + blueprint + lua + package (needs VS 2026, UE 5.6, ue4ss-src)
./deploy.ps1 -Instance $inst                  # core only; -Test adds the test dependent; -Remove takes it all out
./run.ps1 -Instance $inst -Scenario skeleton  # unattended in-game run + check.ps1 (also no-native, no-pak, bad-input, ui, journal, menu, soak)
./run.ps1 -Instance $inst -Scenario skeleton -Target vm   # the same in the Hyper-V VM, while you play (below)
pwsh -File test/unit/run_guard_test.ps1       # run.ps1 refuses while another runner's test mod is enabled (-AllowOtherDrivers)
./check.ps1 -Instance $inst -Scenario skeleton
```

`ue4ss-src/` (ignored) is the pinned UE4SS commit with submodules, as `mods/cpp-spike/build.ps1` clones it; `build.ps1 -Ue4ssSrc <path>` points elsewhere. `run.ps1` posts Enter to the game window's message queue for touchdown (and, in the `journal` scenario, the map key: the letter `IA_Map` is bound to) (no foreground change, so a dialog in front doesn't block it and nothing is typed into another program), and only ever stops the game under the instance; don't type into the game while it runs. Story 15's `ui` scenario also asks for real mouse clicks (`click <x> <y>`, desktop pixels from core's geometry functions): on the host `run.ps1` then brings the game window to the front, moves the cursor and clicks, only while the game is in front (it takes the mouse for a moment); in the VM `tools/vm/vm-click.ps1` does the same inside the VM. Run logs are kept in `dumps/<copy>/nucleus/<scenario>.log` in the workspace.

## Tests in the VM

`run.ps1 -Target vm` runs a scenario in the Hyper-V VM `NNB` (account B; workspace `tools/vm/README.md`, "Single-player tests in the VM") instead of on the host, so it can run while you play on the host with your own account:

```powershell
./run.ps1 -Instance $inst -Scenario skeleton -Target vm
./run.ps1 -Instance $inst -Scenario bad-input -Target vm
./check.ps1 -Log <workspace>\dumps\v8.1.2-build26193463\nucleus\skeleton.vm.log -Scenario skeleton -Target vm
```

- `-Instance` is still the host's copy (absolute, also from a worktree): it names the build and finds the workspace's `tools/`. The VM's copy (`C:\nn\<same name>`) must be the same build; the run refuses otherwise. Nothing of the host copy is read except its exe size, and no host game is started, stopped or checked.
- What's installed is what `deploy.ps1 -Test -Scenario <s>` would install, from this repo's `build/package` (the VM path never builds): `deploy.ps1 -Staged` writes it into a host-side staging folder, which `tools/vm/vm-sp.ps1` copies into the VM copy. UE4SS is switched on for the run; afterwards the VM copy is put back exactly as it was (UE4SS off, no mods), also after a crash or a time limit. An interrupted run is undone by the next one, or by `tools/vm/vm-sp-restore.ps1`.
- Enter at touchdown (and the journal scenario's map key): the test dependent's `request.txt`/`done.txt` are polled in the VM copy over PowerShell Direct, and the key is posted with `tools/vm/vm-key.ps1`; a click request goes to `tools/vm/vm-click.ps1` (a real cursor move and button press in the VM's desktop session, only on the game window), a `shot <label>` request to `vm-screenshot.ps1` (`dumps/<copy>/vm/sp-<label>.png`).
- Time limits are the host's times 1.5 (the VM's game is slower), unless `-TimeoutSec` is given. The log is kept as `dumps/<copy>/nucleus/<scenario>.vm.log`.
- In the VM: `skeleton`, `bad-input`, `no-native`, `no-pak`, `ui`, `journal` (the map key goes through `vm-key.ps1` like Enter). Host only: `soak` (it judges tick costs; refused with `-Target vm`). `check.ps1 -Target vm` makes the one timing assertion inside a functional scenario soft: `ui`'s "no steady-state hud tick over 1 ms" (`WARN hud slow tick ... steady state`) shows as `warn:` instead of failing. `manual` is a hand test and isn't run by `run.ps1` anywhere.
- Builds still happen on the host (`build.ps1`, CPU-heavy: the game you're playing may stutter meanwhile), and the VM's game itself shares the host's CPU and GPU.

## Hand testing

The `manual` scenario is for playing the game yourself with core and the test dependent installed. The test dependent never travels, presses keys or runs timed checks, and never logs `FAIL` for anything you do. It connects to core (`CONNECT ok`, or one line saying why it can't) and keeps a `Nucleus manual: <n>` label in the top-right corner of the HUD through `core.ui.text`, so core attaches it again whenever the game rebuilds or replaces the HUD: first match, back to the menu, new match, death and revive (core logs `DEBUG ui attach 'manual' created|reused ...` each time). `n` counts the attaches. Each attach logs one `ATTACH` line with the HUD, whether it is visible (the menu and the lobby hide it; that's expected) and the label's rectangle. The UI helpers' `DEBUG` lines are on: a `hud tick n=... avg=... max=...` summary once a minute (story 7's 10-minute cost check reads these). While the HUD is visible, it also logs an `OVERLAP` report from `core.ui.debug.overlaps` (story 12) about 1 s and 4 s after an attach: every drawn widget whose on-screen rectangle intersects the label's (`OVERLAP none (...)` when nothing does), plus `OVERLAP near` lines for drawn widgets within 64 px of it. With debug on, core's automatic check also logs `WARN ui overlap 'manual': ...` once per overlapping widget.

```powershell
cd C:\...\nuclear-nightmare\mods\Nucleus
$inst = 'C:\...\nuclear-nightmare\game-instances\v8.1.2-build26193463'
./build.ps1                                     # once, if build/package/ is missing or out of date
./deploy.ps1 -Instance $inst -Test -Scenario manual
..\..\tools\launch.ps1 -Instance $inst          # play; quit the game when done
./check.ps1 -Instance $inst -Scenario manual    # nothing broke: no errors, CONNECT ok, at least one ATTACH
./deploy.ps1 -Instance $inst -Remove            # take core and the test dependent out again
```

The log is `ue4ss\UE4SS.log` in the copy's `NuclearNightmare\Binaries\Win64`, and every launch overwrites it. Save a copy before launching again, and check the copy:

```powershell
$log = "$inst\NuclearNightmare\Binaries\Win64\ue4ss\UE4SS.log"
Copy-Item $log "..\..\dumps\v8.1.2-build26193463\nucleus\manual-$(Get-Date -Format yyyyMMdd-HHmm).log"
./check.ps1 -Log "..\..\dumps\v8.1.2-build26193463\nucleus\manual-<stamp>.log" -Scenario manual
```

`run.ps1` doesn't take `manual`: it waits for an end the manual test never reaches.

## Versioning (story 18, core 0.5.0)

Core only ever adds: no public API (natives, `nucleus.*` modules, channel ops, `core.ui.*`, the `mod.json` contract) is removed or changed incompatibly, before or after 1.0. A replaced API is deprecated: it keeps working, logs one `WARN DEPRECATED <old>; use <new> instead.` line per dependent per session (`lua/pkg/deprecate.lua`), and goes only in a breaking major, announced here. Every public API change needs an entry below and, when it adds something a mod could check for, a `features.lua` entry.

- **Dependents declare a minimum:** `"dependsOn": [{ "id": "nucleus", "version": ">=0.5.0" }]` and the same string in `connect{ need = ">=0.5.0" }`. Any core at or above it satisfies it. `^X.Y.Z` and a bare `X.Y.Z` (what `connect` took before 0.5.0) are read as `>=X.Y.Z`, so mods released with `^0.2.0` / `"0.2.0"` load on 0.5.0 unchanged. Anything else (`~`, `<`, `>= 0.3.0`, `>=1.2`, a non-string, over 64 bytes) is refused at once: `connect` logs one line (`connect: need '<need>' is not a minimum version (want '>=X.Y.Z'). ...`), calls `onFail`, and returns `false, message`. `connect` never raises; it returns `true` when it is waiting for core.
- **Core holds the floor:** `mod.json` `"compat": { "floor": "0.1.0" }`, the oldest need this core still serves (`build.ps1` writes it into `version.lua`; it stays 0.1.0 until a breaking major). The refusals name the older side: `Nucleus <have> is older than <mod> needs (<need>). Update Nucleus.` and, below the floor, `<mod> was made for Nucleus <need>, which this Nucleus <have> no longer supports (oldest: <floor>). Update <mod>.`
- **Feature checks (optional):** `core.has(name) -> boolean`, `core.features() -> { name, ... }` (sorted, a fresh table). Names are API paths generated from the api table `onReady` receives (`lua/pkg/features.lua`): the functions on it (`call`, `ref`, `deref`, `free`), its tables (`clock`, `ui`), and inside a namespace like `ui` every module and function (`ui.text`, `ui.panel`, `ui.button`, `ui.journal`, `ui.hud`, `ui.debug`, `ui.place`, `ui.elements`); a module's own functions aren't listed. Changes inside an existing API get hand-named entries (`features.HAND`, e.g. `ui.panel.reorder`), each added by the story that makes the change (0.8.0 also hand-names the path of every new function, `ui.image.create` ... `ui.button.setTooltip`, so `core.has("ui.image.create")` answers as a dependent expects; plus `ui.overflow` and `ui.button.icon`). `has` is false, never an error, for anything else (non-string, empty, over 64 bytes, nil). The minimum version stays the normal way to depend on a feature. Core's `READY` line lists the same names: `READY version=0.5.0 ... boot=<n> floor=0.1.0 features=call,clock,...`.

## Natives

Registered into every Lua mod's state before its `main.lua` runs (names from `CORE_NAME`):

| Native | Returns | Threads |
|---|---|---|
| `Nucleus_NativeVersion()` | core's version, the UE4SS build it was built for (two strings) | any |
| `Nucleus_ClockMicros()` | microseconds from a monotonic clock (`QueryPerformanceCounter`), a Lua integer. The epoch is arbitrary: only the difference between two calls means anything. No allocation, lock or logging; wrapped as `<lowercase>.clock` `micros()` and `core.clock.micros()` in the `connect` API | any, also during `main.lua` |
| `Nucleus_Ref(address)` | a weak handle (integer) to the live UObject at `address` | game thread |
| `Nucleus_Deref(handle)` | the object, or `nil` once it is gone | game thread |
| `Nucleus_RefFree(handle)` | nothing; idempotent | any |
| `Nucleus_SetObjectives(managerPath, areaName, id1, text1, ...)` | the task count. Fills an `ObjectiveManager_C`'s empty `Objectives` with one objective of 1 to 64 tasks (`UniqueIdentifier` = id, `Description` and `TraitorDescription` = text, `State` and `TraitorState` false) and sets `Area Name`; a manager is filled once only. `Area Name RU` and `RUDescription` stay empty. Host only (refused in a client or standalone world) | game thread, also during `main.lua` |
| `Nucleus_DescribeObjectives(managerPath)` | the manager read back as text, on any machine: `manager<TAB><objectives><TAB><selected><TAB><replicates 0/1><TAB><area>`, then per task `task<TAB><objective><TAB><index><TAB><State 0/1><TAB><id><TAB><text><TAB><TraitorState 0/1><TAB><imposter text>` (tabs and line breaks in values become spaces). Values longer than 512 characters are cut at 512 (on a client they come from another player). Add-only: later versions may append fields or add line kinds, so readers ignore both | game thread, also during `main.lua` |
| `Nucleus_SetTraitorTaskState(managerPath, taskId, state)` | the number of tasks set: `TraitorState` of the filled manager's task(s) with that id (the game's `UpdateTaskTraitorState` sets it on a copy and never writes it back). Host only | game thread, also during `main.lua` |

Natives that take no arguments refuse any (`<fn>: expected 0 arguments, got N`).

The objectives natives (`native/src/objectives.cpp`, map service story 3) exist because Lua can't write the struct array (it crashes the pinned UE4SS). Arguments are strings (and a boolean `state`), never coerced: a path of 1 to 512 printable ASCII characters starting with `/`, an area name of up to 128 and texts of up to 256, ids of up to 64 characters from `[A-Za-z0-9_.-]`, none repeated. The manager is looked up by path and then proven live with the same `GUObjectArray` scan and slot check as `Nucleus_Ref`, its flags read under SEH: a class default object or archetype, an object flagged Garbage (UE5: a destroyed actor until the next GC), PendingKill or Unreachable, and anything that isn't an `ObjectiveManager_C` are refused, each with one `native: REFUSED ...` log line besides the Lua error (once per distinct refusal, up to 256 of them per session; after that every 256th). The writers ask `KismetSystemLibrary` `IsServer`/`IsStandalone` (the `isHost` rule) with the manager as world context. Struct members are found by name prefix (`Actors_`, `Tasks_`, `State_`, `Description_`, `UniqueIdentifier_`, `TraitorDescription_`, `TraitorState_`), exactly one of the expected type each, and every value is built before the first write.

## Map service: host setup (`lua/pkg/map/setup.lua`)

Map service story 5 (`_bmad-output/specs/spec-map-service-v1/`, `map-setup.md` "Order and machine"). No public Lua API: a level that places core's Start marker (`/Game/Mods/<name>/Map/BP_Marker_Start`) gets the setup on its own. Core publishes the shared variable `<lowercase>.map` (`loading`, then `ready` once the setup's hooks are installed, `failed: ...` or `stopped`); the demo map's loader skips its own setup when it reads `ready`. The order:

- every world load (core's one LoadMap post-hook): the game classes the setup spawns are preloaded with `AssetRegistryHelpers:GetAsset` and held by weak handles (`ref.lua`); a LoadMap with no world (failed travel) is one line and nothing else;
- `RegisterInitGameStatePostHook` (after the level loads, before any BeginPlay): the per-world state is reset and the post-hooks on the Start marker's and the game state's `ReceiveBeginPlay` are registered (once per function address);
- the Start marker's `ReceiveBeginPlay`, **host only** (`isHost` = `IsServer` and not `IsStandalone`, cached per world, refreshed in the LoadMap post-hook): `GameStartService_C` at the marker (its ten `*Starts` arrays from the level's PlayerStarts, the `Corrective` one left out; under 20 starts or not exactly one Corrective is one FAIL line), then every kind whose classes are still in memory: items (`Item`: E_MarkerItem 0 Painkillers, 1 Flashlight), one `ObjectiveManager_C` per `AreaName` (Area Name set, `Objectives` filled through the native: story 6 below) and a `BP_CM_V4_C` per Intel marker (`UniqueIdentifer`, `ObjectiveManager`), `BP_Radio_C` per Computer marker (`Location Name`, `HelicopterLocation` from its Landing marker, `ReinformantLocation`, both required), `Lever_Actor_C` (replicating), `AISpawner_C` (stock), `EnemyWaypointActor_C` per marker, and last `BP_GeneratorGameplayNew_C` (`Equipment` = the objects spawned from the markers it lists; an entry that is empty, itself, not core's marker, in another level, listed twice or without a spawned object skips the generator);
- the LoadMap post-hook of that world, the same frame: whatever the travel's GC dropped (in the demo runs, the intel classes); the generator waits for a kind it lists; then the sky (story 8, below), which only this phase spawns;
- the game state's `ReceiveBeginPlay`: `ORDER game state BeginPlay: start marker began first=true GameStartService_C present=<bool> spawned before it: <sections>`.

Every object is spawned at its marker's own transform and gets one `OK|FAIL WIRE ...` line and one position check, `OK|FAIL POS <class> marker=<name> distance=<uu> yaw=<deg>` (0.01 tolerance; the sky's check is grounded instead, below). A bad marker value (unknown Item, an empty, oversized or non-ASCII area name, an id that is empty, over 64 characters, outside `[A-Za-z0-9_.-]` or repeated, a Computer or Generator `LocationName` over 128 characters, a missing Landing or ReinforcementStart, a Landing that isn't a Landing marker of this level, a ReinforcementStart in another level, more than 256 markers of a kind or 64 Equipment entries) is one FAIL line and that object is skipped; a second Start marker is one FAIL line. A client spawns nothing; a stock map gets at most one DEBUG line. Every hook body runs under `pcall`; liveness is `KismetSystemLibrary:IsValid` as a UFunction, called only for a value UE4SS's own `type()` names a UObject wrapper (`UObject`, `AActor`, `UClass`, `UFunction`, `UStruct`, `UEnum`, `UWorld`, `UInterface`, `UDataTable`) and UE4SS's own `IsValid()` accepts: a missing member's placeholder, a struct value, a `TArray` or an out array's `RemoteUnrealParam` entry is `false` without a call into the game (story 17; story 16 found that `IsValid` crashes the game on them), and an error from the UFunction itself is one WARN per session and `false`; no UObject is kept between calls. The Journal map and flags are the section after this one (story 7). Unit tests: `lua test/unit/map_setup_test.lua` (fake level, markers, classes and objectives natives: the value checks, the Corrective count, the host gate, the deferral, the bad-value rows, story 6's fill, mirror, client Area Name, hostile ids and cabin sound, story 8's sky, and story 9's signal and bad-input sweep).

**The map setup signal** (map service story 9, CAP-6; public API, add-only): one shared variable, `<lowercase>.map.setup` (`nucleus.map.setup`), always a string, on every machine. It tells a dependent whether the setup on its own machine has finished, and whether it succeeded, without reading core's internals. Values (one space between fields; `<world>` is the world's path, e.g. `/Game/Mods/DemoMap/Maps/L_DemoMap.L_DemoMap`, always last):

- `none`: this machine has no level with core's Start marker: a stock map, the menu, a failed travel, before the first world, after unload, and when core's map service doesn't run (then `<lowercase>.map` says why);
- `pending <world>`: core's Start marker is in `<world>`, and the setup there hasn't finished;
- `done <world>`: finished with no failure;
- `failed <n> <world>`: finished, and `<n>` >= 1 is the setup's FAIL-line count in that world at that moment (each failure is its own `FAIL` line in the log).

On the host it turns `pending` at the Start marker's BeginPlay and `done`/`failed` at the end of the setup's LoadMap part; on a client `done` (or `failed`, e.g. for a second Start marker) at the LoadMap post-hook, since the objects arrive by replication. A world finishes once: a doubled LoadMap or a later failure changes nothing. Not in it: the 1 s loop (imposter ticks, client Area Name, cabin sound) and the Journal map and flags, which wait for replication, retry or wait for the player; their `FAIL` lines are their own. Each change logs one line, `MAPSETUP signal <value>`; a publish that throws is one WARN line per world, and the setup goes on. A dependent judges only a value naming its own world (the world goes last for that): between custom maps the game passes the menu or lobby, which resets it to `none`. A reader:

```lua
local v = ModRef:GetSharedVariable("nucleus.map.setup")
local status, rest = tostring(v):match("^(%a+) ?(.*)$")
local n, world = nil, rest -- none: world == ""; done/pending: world = rest
if status == "failed" then n, world = rest:match("^(%d+) (.+)$") end -- then compare world with your own world's path
```

**The sky** (map service story 8, ported from the Journal map follow-up; CAP-10): host only, in the LoadMap post-hook of a world holding the Start marker, once per world. The Start marker's BeginPlay never spawns it and never lists it as deferred: spawning the sky there hung the game (the follow-up's first `demo-solo` run, with the class resident). The class `/Game/UltraDynamicSky/Blueprints/Ultra_Dynamic_Sky.Ultra_Dynamic_Sky_C` is preloaded with the others; one that doesn't load is the usual `FAIL WIRE sky: class ... did not load` line. Checked in this order:

- a live `Ultra_Dynamic_Sky_C` already in this world: `OK WIRE sky: the level already has Ultra_Dynamic_Sky_C <path>; not spawning another`, nothing spawned and no time set, whatever the level's Sky markers (a level that places its own sky needs none);
- exactly one Sky marker, else `FAIL WIRE sky: <n> Sky markers in the level (need 1)`;
- `StartHour` a finite number with 0 <= h < 24, else `FAIL WIRE sky marker=<m>: StartHour <v> isn't 0..24`.

Then the sky spawns at the marker's location with rotation (0, 0, 0), `Time of Day` = h * 100 and one `Update Replicated Time` (each under `pcall`; a failed `Update Replicated Time` is one WARN line, the clients follow at its next replication): `OK WIRE Ultra_Dynamic_Sky_C at the sky marker: StartHour=<h> Time of Day=<read> bReplicates=<read> Animate Time of Day=<read> Time Speed=<read>` and one grounded position check, `OK POS Ultra_Dynamic_Sky_C marker=<m> grounded dz=<z - marker z> yaw=<deg>`: not at distance 0 like the other objects, because the class grounds itself in its construction script (`Ground UDS Actor`, V8.1.5: a trace from 50 above to 150 below the actor, then the hit + 90 Z) and its Static root `SkyRoot` refuses to be moved back. It passes when X and Y are the marker's and yaw is 0 (0.01 tolerance), and Z is the marker's (nothing hit) or from marker Z - 60 to marker Z + 140; else one `FAIL POS ... grounded ...` line, and the sky stays. Core never tries to move the sky. A failed spawn is the usual spawn FAIL line; a `Time of Day` that can't be set or reads back other than h * 100 is one `FAIL WIRE sky marker=<m>: Time of Day ...` line and the sky stays. Clients spawn nothing (they get it by replication), and the game itself sets its speed from the lobby's night cycle (`UpdateFriendlyFire`): core never touches `Time Speed` or `Animate Time of Day`. Tester time control (F7/F8, `skytime`) stays test tooling in `mods/map-spike`.

**Objectives, imposter ticks, client Area Name, cabin sound** (map service story 6):

- **Host fill**, in the intel section right after each `ObjectiveManager_C` spawns: one objective with one task per valid Intel marker of that `AreaName` through `<name>_SetObjectives` (id = `UniqueIdentifier`; text = `TaskText`, or when it is empty `Recover the classified material: ` + the id split at lower-to-upper case, `DemoIntelNorth` -> `Demo Intel North`; the native copies it into the imposter text too). A `TaskText` over 256 characters or not printable ASCII is one `FAIL WIRE intel marker=<m>: TaskText ...; skipped` line and the marker is left out. Lines: `OBJECTIVES "<area>" before the fill: objectives=0 selected=<n>`, `OK OBJECTIVES "<area>" filled by <name>_SetObjectives: objectives=1 tasks=<n> (<ids>)` and `OK OBJECTIVES "<area>" read back: objectives=1 selected=0 replicates=<bool> area="<area>" tasks=[<id> State=false "<text>" imposter "<text>" TraitorState=false; ...]` (`<name>_DescribeObjectives`). A refused fill or a readback that differs is one `FAIL OBJECTIVES` line; the rest of the setup goes on.
- **The 1 s loop**: a `LoopInGameThreadWithDelay` registered from core's LoadMap post-hook (game thread) when the world holds the Start marker, cancelled in any other world, when LoadMap gives no world, and on unload (`MAP.start(world)`/`MAP.stop` in `main.lua`). Per-world state is paths and plain values only; every part runs under `pcall` and a fault is one `FAIL <part> loop part threw` line per world.
- **Imposter ticks** (host): for each manager core filled in this world, every task whose `State` differs from its `TraitorState` gets `<name>_SetTraitorTaskState(path, id, State)` (the game's `UpdateTaskTraitorState` writes a copy): `OK TRAITOR "<area>" task <id> State=true -> TraitorState=true (1 task)` or one `FAIL TRAITOR` line per change (not retried every second). Stock maps' managers, and any manager core didn't fill, are never touched; a manager that can't be read any more is dropped with one WARN line.
- **Client Area Name** (not replicated): on a non-host machine in a level with the Start marker, each `ObjectiveManager_C` of this world whose `Objectives` has arrived gets `Area Name` (FText, locally) from the local Intel markers its task ids name: `OK AREANAME <manager> Area Name="<area>" set locally (...)` (or `... already`). The ids come from the host and are untrusted: at most 64 tasks are read, each id must pass the id check (1 to 64 of `[A-Za-z0-9_.-]`) before it is used as a lookup key, and an oversized or bad id, an id matching no local marker, or ids naming two areas is one `FAIL AREANAME <manager>: ...; left alone` line. Ids never become paths, code or sizes. The loop stops looking once every local area is set (an area counts only through markers the host keeps: a bad AreaName, id or TaskText leaves a marker out on both). A stock map's LoadMap resets the per-world state, so a client that comes back to the same level starts fresh (InitGameState runs only on the server).
- **Cabin sound** (every machine, a local effect, not an actor): the game's `/Game/Sounds/helicopter-loop1` with `/Game/RealFootsteps/ATT_Footstep` (loaded with `AssetRegistryHelpers:GetAsset`) at the Corrective PlayerStart + (-28.12253, -1452.6485, 578.62) and + (-28.12253, 489.3703, 752.874), through `GameplayStatics:SpawnSoundAtLocation`; retried once a second for up to 30 s per world. `OK CABIN sound A|B at (<x>,<y>,<z>): <component path> (helicopter-loop1, ATT_Footstep)` per spot; a failure is a `FAIL CABIN` line on the host and a plain `CABIN ... (not judged on a client)` line on a client; no Corrective start or more than one is one line per world.
- A stock map (no Start marker) gets none of the OBJECTIVES, TRAITOR, AREANAME or CABIN lines.

## Map service: Journal map and flags (`lua/pkg/map/journalmap.lua`)

Map service story 7 (CAP-9), ported from the demo map's Journal map follow-up (`docs/custom-maps.md` in the workspace). No public Lua API, no test code; every machine, only in a level that holds core's Start marker, reading core's Map marker (`Picture`, `RectMin`, `RectMax`, `KeepPicture`) and Location markers (`LocationName`). The order:

- core's one LoadMap post-hook: a world with the Start marker gets fresh per-world state and the loop (`LoopInGameThreadWithDelay`, 1 s, game thread); any other world, or a LoadMap without a world, stops it. Unload stops it too;
- the loop, once per world each: one local `LevelLocationMap_C` per Location marker (`Name` = `LocationName`, `RUName` the same text: `MapUI_C` shows `RUName` when the culture is `ru`); the picture, loaded with `AssetRegistryHelpers:GetAsset` and kept in the Map marker's `KeepPicture` (or GC drops it during a long lobby); the `MapUI_C` and `MapWidget_C` `Construct` post-hooks, registered once their classes load (by function address);
- `MapUI_C:Construct`: `Image` gets the picture (`SetBrushFromTexture`). Unless the rectangle is the game's own (within 1 m: then only the picture), `Image`'s slot is placed over the rectangle in the game's projection, the map is pre-zoomed (min(736 / w, 611 / h) x 0.92, clamped 1..35) and panned to it (`Scale X/Y`, `Translation`, `CanvasPanel_15`'s render transform), and every icon at the projection's origin (352, 220) whose alignment reads (0, 0) gets (0.5, 0.5); `MapWidget_C:Construct` applies the view again;

Lines: `MAP picture <path> loaded (<w> x <h>)`, `MAP <n> area flag(s) spawned locally: ...`, `MAP MapUI_C Construct: picture, slot ..., zoom ..., icons centred <n>, already <n>, other <n>` (or `picture only`, `stock (...)`; at most three per class and world), `MAP MapWidget_C Construct: view ...`, `MAP centred <n> icon(s) added after Construct`, and once per world `MAP <n> icon(s) already centred (alignment 0.5, 0.5) by the game: the centring fix isn't needed for them` (when a patch fixes the game's anchoring: the fix can go) and `MAP <n> icon(s) with another alignment left as they are`.

## Native hardening

Every native validates its arguments and answers bad input with one Lua error naming the function and the problem (for example `Nucleus_Ref: address 0x10000 is not a live UObject (not in GUObjectArray)`). `Nucleus_Ref` never reads through the address it gets: it looks it up in `GUObjectArray` by pointer comparison (a scan from the last slot down: objects created since the game started usually sit near the end, though the array reuses freed slots, so after a map change a new object can sit anywhere; a miss still compares every slot; its cost is logged as `REF_COST` at call counts 1, 2, 4, ...). Engine-memory reads run under SEH as a last resort; a fault is logged as `native: FAULT ...` and the call fails cleanly. Handles are integers in `1 .. 2^53-1`; anything outside that range is an error, an unknown handle in range is `nil` (`Deref`) or ignored (`RefFree`).

## Settings service (`core.settings`, Mod Manager story 5, core 0.9.0)

Every mod's settings in one place: declared in the mod's `mod.json`, kept by core in `Mods/<Folder>/settings.json`, checked, and announced to the mods when they change. Core's own Lua state owns the values (`lua/pkg/settings/store.lua` and `schema.lua`, one writer for everyone); each dependent's `core.settings` (`lua/pkg/settings/client.lua`) caches its own and reaches core only through two channel ops and a shared revision counter. Nothing is ever executed: `mod.json`, `settings.json` and the channel payloads go through one bounded JSON reader (`lua/pkg/json.lua`).

**Addressing.** A mod is its folder under `ue4ss/Mods/` (`^[A-Za-z0-9_-]{1,64}$`, checked before any path is built; core's `Mods/` comes from its own script path). A dependent's own folder is found when it calls `connect`: the first `Mods/<Folder>/Scripts/` in the call stack that isn't core's. If there is none, `get`, `getAll`, `set` and `watch` raise `nucleus.settings.<fn>: own mod folder unknown`; `describe` and `setFor` still work.

**Declarations** (`mod.json` `settings`, an object, at most 64 entries, declaration order kept). Key `^[A-Za-z][A-Za-z0-9_.]{0,63}$`; `type` `bool | int | number | enum`; `default` of that type within its bounds (`null` only with `source`); `min`/`max` (int: integers; number: finite; `min <= max`); `step` (number only, `> 0`; a hint for the Manager); `values` (enum: 1 to 32 unique strings of at most 64 bytes, the default among them); `label` (at most 64 bytes; missing: the key); `help` (at most 256 bytes); `changeable` `anytime | menu | lobby | restart` (missing: `restart`); `scope` `client | host | all`; `source` (at most 32 bytes). Unknown keys are ignored. A bad entry is left out with one `WARN settings: <folder>: setting '<key>' left out: <why>`; the rest of the mod still works.

**Windows.** `anytime` and `menu` apply live (watchers are called); a `menu` setting is refused (`locked`) unless the current world is the title screen (`NewMainMenu`, from core's LoadMap post-hook). `lobby` is always refused (`locked`) in this version: core has no lobby phase yet. `restart`: the value is saved, `get` keeps returning the value loaded at session start, the description shows `pendingRestart = true` (and the saved value as `saved`) while they differ, and watchers aren't called. A setting with `source` is read-only: its value is absent, it is never written, and `set` is refused (`read-only`).

**Values file** `Mods/<Folder>/settings.json`: a flat JSON object of the values that differ from the defaults, in declaration order, at most 16,384 bytes. Read on a folder's first use in a session and after each write; every entry is checked again, and unknown, read-only, wrong-type or out-of-range entries are dropped (one `WARN` listing them). A missing file: the defaults, with one info line per mod per session (`settings: <folder>: no settings.json; using the declared defaults`). A corrupt or invalid one: the defaults with one `WARN` per mod per session. A write goes to `settings.json.tmp` (written, flushed, closed, read back and compared), then the old file becomes `settings.json.bak`, the tmp file becomes `settings.json`, and the `.bak` is removed; if `settings.json` is missing and a `.bak` is there (a write cut short between its renames), the `.bak` is restored first. Any failure leaves the previous file and the value in memory as they were, and is reported (`write-failed`, and one `WARN`). Core never writes, renames or removes any other file.

**Channel ops** (core's state, game thread; the request cap stays 4,096 bytes):

| Request | Reply |
|---|---|
| `settings-get:<Folder>` | `ok:<description as JSON>` |
| `settings-set:{"mod":"<Folder>","key":"<key>","value":<value>}` | `ok:<the entry as JSON>` after a successful write; then `nucleus.settings.rev` is incremented |

Errors: `err:bad-request`, `err:unknown-mod`, `err:no-settings`, `err:unknown-key`, `err:bad-value`, `err:read-only`, `err:locked`, `err:write-failed`, and `err:internal` (the settings service is not running, or a reply could not be encoded), each followed by a detail of at most 64 printable bytes. `nucleus.settings.rev` is an integer shared variable: it starts at its previous value (a hot reload keeps it rising) or 0.

**Description** (the `settings-get` reply and `describe`'s return): `{ id, name, folder, settings = { { key, type, default, min, max, step, values, label, help, changeable, scope, source, value, readOnly, restart, pendingRestart, saved }, ... in declaration order }, problems = { strings } }`. `restart` is true for `changeable = "restart"`; `saved` is present only while `pendingRestart` is.

**`core.settings`** (game thread, after `connect`; `core.has("settings")`):

| Call | Result |
|---|---|
| `get(key)` | the own mod's value (`nil` for a read-only one) |
| `getAll()` | a copy of the own mod's values, `key -> value` |
| `set(key, value)` | `true`, or `false, "<code> <detail>"` for `read-only`, `locked`, `write-failed` |
| `setFor(folder, key, value)` | the same for another mod (for the Mod Manager) |
| `describe(folder)` | the description as plain Lua tables, or `nil, "<code> <detail>"` for `unknown-mod`, `no-settings` or core not answering |
| `watch(fn) -> token` | `fn(key, value)` under `pcall`, once per changed live key, for changes by anyone (the own `set` included, before it returns) |
| `unwatch(token)` | `true`, or `false` for a token that isn't watching |

Caller bugs raise one clean error, `nucleus.settings.<fn>: <problem>`: a non-string or empty key, an unknown key, a bad value (wrong type, out of range, not in `values`, NaN or infinite), a bad folder (`..\x`, over 64 bytes), an unknown folder or one without settings (for `set`/`setFor`), a non-function watcher, a non-integer token, extra arguments, a call before `connect` or off the game thread. The cache refreshes after an own `set`, in `get`/`getAll` when `nucleus.settings.rev` moved (one shared-variable read), and from a 500 ms `LoopInGameThreadWithDelay` poll that runs only while the mod has a watcher (generation-guarded; never `LoopAsync`).

In game: `bad-input` (below).

## Host replicated state (`core.net`, core story 22, core 0.11.0)

The host publishes a few integers that modded clients read during the match, with no RPC of the mod's own (CAP-11; `_bmad-output/specs/spec-core-v0/net-contract.md`, "Net-1"). Core's own Lua state owns the state on every machine (`lua/pkg/net/host.lua`); each dependent's `core.net` (`lua/pkg/net/client.lua`) reads it from four shared variables and publishes only through the channel op `net-publish`. One pure module (`lua/pkg/net/state.lua`) validates, encodes and decodes for the host, the client and the unit tests.

**The actor.** `/Game/Mods/Nucleus/NucleusNet` (`NucleusNet_C`, CoreGen): replicated, always relevant, two replicated strings `State` and `CoreVersion` (no RepNotify), written only through `Nucleus_NetSetState(State)` and `Nucleus_NetSetVersion(CoreVersion)`. Core spawns one in each world it hosts (`isHost` = `IsServer and not IsStandalone`, map/setup.lua's per-world cache), from the `LoadMap` post-hook, with no owner, retried each second up to 5 tries (then one `ERROR`); never on a client or in the menu. A client finds the host's through `NotifyOnNewObject` on the full class path, or a `FindAllOf` fallback at most every 2 s while none is held (full class path, this world, no authority), holds it only as a weak handle checked with the `KismetSystemLibrary:IsValid` UFunction, and polls it every 250 ms (`LoopInGameThreadWithDelay`). A `CoreVersion` other than its own (exact string) makes it ignore the actor, with one `WARN` per world.

**`State`** (at most 8,192 bytes): comma-separated `#<n>=<mod id>` headers (n = 1..16, in first-publish order on the host, per world) and `<n>.<name>=<int>` values, so a long namespaced id is sent once (`#1=skeltest,1.revivesN=8`). A client checks everything again: the whole string is ignored when over 8,192 bytes; a header whose id isn't in normalized form (and its entries), an entry whose number has no header, a bad name or value, entries past a cap, duplicates after the first, and anything else are dropped, each with at most one `WARN NET dropped ...` per key (per actor for a whole-string reject) per minute.

**Keys, values, caps.** Key `<mod id>.<name>`, split at the last dot: the mod id is the publisher's own (`mod.json` `id` of the folder that called `connect`, normalized by `lua/pkg/modid.lua`: `<owner>.<mod>` up to 200 characters, or a legacy bare `[a-z0-9-]{1,64}`); the name `[A-Za-z0-9_]{1,32}`. The public API never takes a mod id: `publish` uses the `id` in `Mods/<Folder>/mod.json`, so a publishing mod must ship `mod.json` next to its `Scripts/`, call `connect` from its own `Scripts/`, and live in a folder named `[A-Za-z0-9_-]{1,64}`; otherwise `publish` raises (`read` and `watch` still work). Values: integers in -2147483648..2147483647 (a float with an exact integer value counts). Caps: 16 keys per mod, 64 keys in all, 16 publishing mods per world. Values belong to the host world they were published in: every `LoadMap` clears them (lobby and match are one world). A `publish` before the actor exists is written when it spawns.

**`core.net`** (game thread, after `connect`; `core.has("net")`):

| Call | Result |
|---|---|
| `publish(key, value)` | `true` on the host; `false, "standalone"` in the menu; `false, "no-world"` before the first world; raises `nucleus.net.publish: only the host publishes (this machine is a client)` on a client |
| `read(key, min, max)` | the value, or `nil, "absent"` (not published), `"out-of-bounds"` (outside the reader's `min..max`; one `WARN` per key per minute), `"no-state"` (no host state here yet, or the menu) or `"version"` (the host runs another core version) |
| `watch(key, min, max, fn) -> id` | `fn(value)` or `fn(nil, reason)` under `pcall` on the game thread, at the first poll and whenever that result changes (a 250 ms poll that runs only while a watch exists; a fault logged once per watch); at most 64 per mod |
| `unwatch(id)` | `true`, or `false` for an id that isn't watching |
| `role()` | `"none"` (before the first world), `"standalone"`, `"host"` or `"client"` |

Caller bugs raise one clean error, `nucleus.net.<fn>: <problem>`: another mod's prefix, a malformed key or name, a non-integer or out-of-range value (`nil`, `"8"`, 2.5, NaN, infinity, 2^31), a cap reached, bounds that aren't integers or with `min > max`, a non-function `fn`, a non-number id, extra arguments, a call before `connect` or off the game thread, and `publish` from a mod without a valid `mod.json` `id` (it can still read and watch).

**Channel op and shared variables.** `net-publish:<key>=<value>` (payload at most 246 bytes; any mod in the process may call it, so core checks the key, the value, the role and the caps again): `ok:published` or `ok:unchanged`, else `err:bad-request`, `err:client`, `err:standalone`, `err:no-world` or `err:cap`, with a detail. Shared variables (strings, written by core's state): `nucleus.net.role`, `nucleus.net.status` (`ok`, `no-state`, `version`), `nucleus.net.snapshot` (the clean values in `State` form) and `nucleus.net.gen` (an integer, +1 on any change; dependents decode the snapshot again, with the same checks, only when it moves).

Unit tests: `texlua test/unit/net_test.lua` (the normalizer's cases, every row of the story's I/O matrix: encode and bounded decode, caps, hostile `State`, bounds, version mismatch, watch change detection, the limiter; `host.lua` over fake objects and `core.net` wired to it). In game: `bad-input` (`net-*` cases). Two players: `test/pair/nucleus-scenarios.ps1`.

## Player presence (`core.net`, core story 23, core 0.12.0)

The host learns which connected players run which mods, in which version, so it relies on a player's own machine only when that machine can play along (CAP-12; `_bmad-output/specs/spec-core-v0/net-contract.md`, "Net-2"). Core's own Lua state owns it on every machine (`lua/pkg/net/players.lua`, ticked on `core.net`'s 250 ms loop and reset from the same `LoadMap` post-hook); dependents read a snapshot through `core.net` (`lua/pkg/net/client.lua`). One pure module (`lua/pkg/net/presence.lua`) validates, encodes and decodes for the host, the client and the unit tests.

**What a machine reports: its local list.** Nucleus itself (`nucleus=<version>`) plus every connected dependent: at `connect`, `core` reads the dependent's own `Mods/<Folder>/mod.json` (`id`, `version`, and the optional `netCompat`) and registers it with the channel op `net-mod`; when the mod unloads it sends `net-mod-off`. A `version` that isn't strict `x.y.z` keeps the mod out (one `WARN` at `connect`); an invalid `netCompat`, or one above `version`, is left out (one `WARN`). At most 32 entries. Mods without Nucleus are not reported.

**The actor.** `/Game/Mods/Nucleus/NucleusPresence` (`NucleusPresence_C`, CoreGen): replicated, always relevant, a replicated `CoreVersion` written only through `Nucleus_PresenceSetVersion`, and one reliable server event `Nucleus_SV_Report(Report)`. Its Blueprint body checks `Len(Report)` before any Lua copies it: over 8,192 characters it calls `Nucleus_PresenceIn("", Len)`, otherwise `Nucleus_PresenceIn(Report, Len)`; core's Lua post-hooks only `Nucleus_PresenceIn`, under `pcall`. On the host (`isHost`), every poll walks `NetDriver.ClientConnections` and spawns one actor per client player controller, owned by it (`SetOwner`), with `CoreVersion` set; the host's own controller gets none, and nothing is spawned on a client or in the menu. A modded client finds its own actor (`NotifyOnNewObject` or a `FindAllOf` fallback every 2 s: full class path, this world, no authority, owned by its player controller), ignores it when its `CoreVersion` isn't its own (one `WARN` per world: it never reports), and calls `Nucleus_SV_Report` with its list once it holds the actor and again 2 s after any change to the list.

**On the host.** A report counts only on an actor in core's own per-world table; the player is that actor's owner's `PlayerState` (`GetPlayerId`), never anything in the report. At most 1 report per player per second and 10 per minute; at most 32 pairs and 8,192 bytes (more rejects the whole report); a bad pair (an id not already in normalized form, a version that isn't strict `x.y.z` with parts 0..999, a `netCompat` above its version) is dropped and the rest kept; on a duplicate id the first wins. Every reject logs at most one `WARN PRESENCE ...` per player per minute. An accepted report replaces that player's record. A controller gone from `ClientConnections` loses its record (`left` for each of its mods) and its actor (`K2_DestroyActor`). At most 64 client records per world (then one `WARN`). Records belong to the world: every `LoadMap` clears them. The local player's record is the local list (the host's, and in the menu the only one).

**Report format.** `<id>=<version>` or `<id>=<version>/<netCompat>`, comma-separated: `nucleus=0.12.0,skeltest=0.1.0,nuclearnightmare-community.skeltest-ns=0.3.0/0.1.0`.

**`netCompat`** (optional `mod.json` field): the oldest version of the same mod this version works with over the network, strict `x.y.z` and not above `version`. Without it: `0.<minor>.0` for 0.x, `<major>.0.0` from 1.0. Two machines are compatible for a mod when each version is at least the other's `netCompat`, so the defaults mean "same `major.minor`" below 1.0 and "same major" from 1.0. That is the one rule; core never refuses or kicks anyone over it.

**`core.net` additions** (game thread, after `connect`; `player` is a `PlayerState` or its integer `PlayerId`):

| Call | Result |
|---|---|
| `presence(player, modId)` | the player's version of `modId` (a string), or `nil, "absent"` (unknown player, unmodded player, mod not in the record), or `nil, "no-world"` before the first world. Host and menu; raises `nucleus.net.presence: only the host knows presence (this machine is a client)` on a client |
| `watchPresence(modId, fn) -> id` | `fn(event, playerId, version, previous)` under `pcall` on the game thread for `"joined"`, `"changed"` and `"left"` (`version` is `nil` on `left`), the local player included; at most 64 per mod (apart from `watch`'s 64); the id works with `core.net.unwatch`; raises on a client |
| `compatible(player, modId)` | `true`, or `false, "absent"` (either machine lacks the mod), `false, "incompatible"` or `false, "no-world"`, comparing this machine's entry with the player's; the local player is compatible with itself when the mod is installed. Raises on a client |
| `versionsCompatible(aVersion, aNetCompat, bVersion, bNetCompat)` | `true` or `false` by the rule above (`nil` netCompat = the default); pure, works anywhere (off the game thread too); raises on a malformed version or a netCompat above its version |

Caller bugs raise one clean error, `nucleus.net.<fn>: <problem>`: a `player` that isn't a live `PlayerState` or an integer `PlayerId`, a `modId` that isn't a string, is empty, over 200 characters or not a normalized net id (`Bad_Id`, a 65-character bare id), a non-function `fn`, the 65th presence watch, extra arguments, a call before `connect` or off the game thread.

**Channel ops and shared variables.** `net-mod:<id>=<version>[/<netCompat>]` (`ok:registered`, `ok:unchanged`; `err:bad-request` for an oversized payload, no `=`, a bad id, version or netCompat, or core's own id; `err:cap` for the 33rd entry) and `net-mod-off:<id>` (`ok:removed`, or `ok:unknown` for an id that isn't there; `err:bad-request` for a bad id). Shared variables: `nucleus.net.presence` (the snapshot: `<local PlayerId or ->:<local list>` then `;<PlayerId>:<record>` per client player, in `PlayerId` order; empty on a client and before the first world) and `nucleus.net.presence.gen` (+1 on any change; dependents decode the snapshot again, with the same checks, only when it moves).

Unit tests: `texlua test/unit/net_presence_test.lua` (every matrix row that needs no second machine: versions, netCompat, report caps, bad pairs, duplicates, the rate limit on a fake clock, the record diff, the snapshot; `players.lua` over fake objects: the local list and its ops, spawn and owner, the report hook's identity, the forge sequence, leaves, the cap, the client's own actor, the version mismatch, the sends; the dependent's calls wired to it). In game: `bad-input` (`net-presence-*` cases). Two players: `test/pair/nucleus-scenarios.ps1`.

**Pair runs** (friends-only lobby, `tools/vm/pair.ps1`, B = the VM; hold `dumps\vm.lock`; ask before a host game runs):

```powershell
./tools/vm/pair.ps1 -Scenario presence -ScenarioFile mods/Nucleus/test/pair/nucleus-scenarios.ps1          # B modded: join, forge, leave
./tools/vm/pair.ps1 -Scenario presence-vanilla -ScenarioFile mods/Nucleus/test/pair/nucleus-scenarios.ps1  # B vanilla: an actor, no record
```

`presence`: the host runs `presence-host` (logs every `PRESENCEEV` event and, timed from B's `joined`, the forge steps' records and `COMPAT` lines, then `PRESENCE forge-done`); B runs `presence-client`: 5 s after it holds its own actor it sends the forge sequence on that actor, 2 s apart (step 0 core's own report, 1: 33 valid pairs, 2: 9,000 × `a`, 3: bad pairs, 4: 50 × `nucleus=<v>,skeltest=7.7.7` in one tick), checks that `presence`, `watchPresence` and `compatible` raise the client error, and 10 s after step 4 leaves with `OpenLevel(NewMainMenu)`. pair.ps1's `LeaveAllowed` key lets the run end with one player after `PRESENCE forge-done`. `presence-vanilla`: an unmodded B must stay in the session; the host spawns its actor, owned by B's controller, and B never gets a record.

### Journal regions (story 19, core 0.6.0)

Named parts of the open Journal for `core.ui.place`, all in the journal host's canvas units (the root canvas of `Journal_C.MapWidget`). `core.ui.elements("journal")` lists them; `core.has("ui.journal.regions")` tells a dependent they exist.

| Region | Part of the binder | Kind |
|---|---|---|
| `cover` | the dark binder cover the pages sit on (`NN_BinderCover`) | exact |
| `page-left` / `page-right` | the left page (the map) / the right page (match, tasks, ammo) (`NN_LeftFieldPaper` / `NN_RightFieldPaper`) | exact |
| `binder` | both pages with the spine: per edge, the outer edge of the two page papers | exact |
| `map` | the map square (`MapUI` in `NN_FieldMapPlane`, 736x611 at scale 1; zoom and pan never move it) | computed (story 20), verified once by measuring |
| `map-header` | the MAP / time / DAY bar (`TextBlock_86`'s parent's parent, a `Border`) | measured |
| `match` | the MATCH block with the players (`StackBox_1`'s parent's parent, a `VerticalBox`) | measured |
| `tasks` | the CLASSIFIED MATERIALS block (`GraphicsScroll`'s third parent, a `HorizontalBox`) | measured |
| `ammo` | the dark AMMO box (`NN_AmmoCarbonBacking`) | measured |

```lua
{ host = "journal", corner = "bottom-left", region = "page-left", inset = "tight" }   -- inside a region
{ host = "journal", corner = "top-right" }                                             -- a plain corner: the cover's
{ host = "journal", near = "map", side = "below", align = "center", gap = "tight" }    -- next to a region
```

- **Exact** regions read the live `CanvasPanelSlot` of their widget on every placement (its anchors and offsets; it must be stretched on both axes). The element gets a point anchor on the region's corner or edge, so it is right before the first paint and at any resolution or aspect.
- **Computed** (story 20, `map` only): before the first paint, from the live slots of the left page's layout (`MapUI` → `NN_FieldMapPlane` → `NN_FieldMapViewport` → `VerticalBox_3` → `HorizontalBox_1`, the header's height after a layout prepass) and the map box's shrink-only rule `scale = min(1, availW/736, availH/611)`, one formula at every aspect. The canvas size is the viewport's size over its scale, less the live offsets of the Journal's `WidgetSwitcher_0` slot (about 6.1 x 2.0 units). After the first paint core waits until the drawn rect is valid and equal on two consecutive journal ticks, compares once (one `WARN journal region 'map' computed ... but drawn ...` if an edge is more than 1 unit off) and follows the drawn rect from then on, with the measured cadence. If a link or the layout's shape differs (a patch), one `WARN journal region 'map' can't be computed (...)` per Lua state and `map` is measured instead.
- **Measured** (content-sized: `map-header`, `match`, `tasks`, `ammo`) regions sit inside box panels, so only geometry knows them: `Nucleus_RectIn` on core's ModActor, after the new Journal's first paint (every map open is a new Journal). Until the rectangle is valid (finite, over 1 unit both ways) their elements stay collapsed. Core re-reads such a region every journal tick until it is valid, then every 4 ticks (2 s), at most once per tick, and re-places its elements only when the rectangle changed.
- **When attached** (story 20): journal elements are attached in a `Journal_C:Construct` post-hook, inside the game's `AddToViewport`, before the Journal's first paint. Only element classes already cached are used there (never a load); an element whose class isn't cached yet is attached when the poll sees the Journal (`opened`), which also writes the attach line (`... (construct)`). The `opened` event itself still comes from the poll, and no dependent code runs in the hook.
- **Corners:** the first element of one mod in a region's corner sits `inset` from both edges (`tight` 8, `normal` 16, `loose` 32; default: the intent's `gap`), each later one `gap` after the previous, each `inset` from the side edge. Stacks are per (host, region, corner). On the HUD inset is the gap, so HUD numbers are unchanged.
- **A plain journal `corner`** (no `region`) is a corner of `cover` (0.6.0; before, the screen corner outside the binder).
- **Bad input** raises like any bad intent: an unknown region (`unknown region 'spine' (valid: ammo, binder, cover, map, map-header, match, page-left, page-right, tasks)`), `region` or `inset` on the HUD (`region is not available on host 'hud' (journal only)`), a bad `inset`, a journal `near` that isn't a region (`unknown near region 'crosshair' (valid: ...)`).
- **After a game patch** a region widget that is missing or has another type logs one `WARN journal region '<name>': ... (<widget path>)` per Lua state and its elements stay collapsed; there is no fallback region. Re-check the regions after every patch (`tools/diff-dumps.watch.json` in the workspace lists what to compare).
